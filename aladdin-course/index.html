The Shared Memory

All five components read from and write to one shared object called the Zustand store. Think of it as a whiteboard in the middle of the room — any component can write on it, any component can read from it.

CODE 

const useStore = create<AppState>()(
  persist(
    (set, get) => ({
      jobs: [],
      selectedJob: null,
      filters: {},
      setJobs: (jobs) => set({ jobs }),
      setSelectedJob: (job) =>
        set({ selectedJob: job }),
    }),
    { name: 'aladdin-store' }
  )
);
PLAIN ENGLISH

create<AppState>()() → Create a global store that any component can subscribe to — when it changes, every listening component re-renders automatically

persist(...) → Automatically save state to localStorage — so if you refresh the page, your selected job and filters are still there

jobs: [] → Start with an empty list of jobs (filled in when the page loads)

selectedJob: null → Nothing is selected yet — clicking a job card sets this

filters: {} → No filters applied yet

setJobs / setSelectedJob → Functions that components call to update the shared memory — like writing on the whiteboard

'aladdin-store' → The localStorage key used to save and restore this state

What is Zustand? "Zustand" is German for "state." A library built by the open-source community. "State" just means "the current values the UI needs to display." Managing it in one place means components never fall out of sync.

The Adapter Pattern

All 6 adapters speak the same language — they all implement a SourceAdapter interface with a poll() method. Like a universal power adapter: the wall socket is different in every country, but the plug coming out is always the same.

CODE 

export class GreenhouseAdapter
    implements SourceAdapter {
  name = 'greenhouse' as const
  private lastRequestAt = 0

  private async rateLimit():
      Promise<void> {
    const elapsed =
      Date.now() - this.lastRequestAt
    if (elapsed < RATE_LIMIT_INTERVAL_MS) {
      await new Promise((r) =>
        setTimeout(r,
          RATE_LIMIT_INTERVAL_MS - elapsed))
    }
    this.lastRequestAt = Date.now()
  }

  async poll(target: PollTarget):
      Promise<NormalizedJob[]> {
    await this.rateLimit()
    // ... fetch and normalize jobs
  }
}
PLAIN ENGLISH

implements SourceAdapter — This class signs a contract: it will have a poll() method that returns normalized jobs — same shape as every other adapter.

name = 'greenhouse' — Self-identification tag used in logs and task routing so the system knows which adapter ran.

lastRequestAt = 0 — Timestamp of the last API request — used to enforce politeness delays between calls.

rateLimit() — Before every request, check: has enough time passed? If not, wait. This prevents getting blocked by Greenhouse's servers.

elapsed < RATE_LIMIT_INTERVAL_MS — Have we waited long enough since the last request?

await new Promise(...) — Pause execution for the remaining wait time — this is how JavaScript "sleeps" without freezing the whole program.

this.lastRequestAt = Date.now() — Record that we just made a request so the next call can calculate the wait correctly.

poll(target) — The main method: given a company, fetch all their open jobs and return them in the standard format.

The Adapter Pattern is one of the most powerful in software engineering. Adding support for a new job source means writing ONE new class that implements SourceAdapter — the rest of the pipeline just works. You could ask an AI to "create a LinkedInAdapter that implements SourceAdapter" and the entire system would pick it up automatically.

The Editor Who Never Apologizes

After jobs are fetched, every single one runs through the cleanup filter. It's intentionally aggressive — missing a good job is fine, but showing you a bad one wastes your time.

1
🚫 Auto-Delete: Senior titles

Title contains "Senior", "Lead", "Principal", "Manager", "Director", "VP" — immediately rejected. These are not entry-level roles regardless of the job description.

2
🚫 Auto-Delete: Too much experience required

More than 2 years of experience explicitly stated in the description — auto-deleted. The filter parses the description looking for phrases like "5+ years required."

3
🚫 Auto-Delete: Wrong field

Healthcare, finance, HR, sales, marketing, legal — out. Aladdin is for software engineers, not every job that uses a computer.

4
🚫 Auto-Delete: Bad description

Fewer than 3,000 characters or placeholder text detected (e.g., "click to apply", "view full description") — the job content didn't load properly, so it gets dropped.

5
✅ Passes all checks

Job survives every filter — it's saved to the database and appears in your feed. Only the best reach you.

The Filter in Code

CODE 

export const MIN_DESCRIPTION_LENGTH
  = 3000;

export const CONFIDENCE_THRESHOLDS = {
  description: 0.6,
  date: 0.5,
  location: 0.4,
} as const;

const PLACEHOLDER_PATTERNS = [
  /view full description/i,
  /click to apply/i,
  /please log in/i,
  /sign in to view/i,
] as const;
PLAIN ENGLISH

MIN_DESCRIPTION_LENGTH = 3000 — Reject any job with fewer than 3,000 characters in the description. A real job posting is detailed; a stub is not.

CONFIDENCE_THRESHOLDS — Minimum confidence scores for scraped data. If the scraper isn't confident enough it got the real content, the job is rejected.

description: 0.6 — Must be at least 60% confident the description field is real content, not garbled HTML or an error message.

PLACEHOLDER_PATTERNS — Regex patterns that identify fake descriptions. If these phrases appear, the job page didn't load properly.

/view full description/i — Case-insensitive match for this exact placeholder phrase. The /i means it catches "View Full Description" and "VIEW FULL DESCRIPTION" too.

The philosophy: false negatives (missing a good job) are acceptable. False positives (keeping a bad job) are not. When in doubt, delete.

The Fingerprint System

The same job often appears on multiple sources simultaneously. Before saving any job, the system generates a unique fingerprint (a hash) and checks if it already exists.

1
Take the raw job data

Combine: job title + company name + location + full description. These four fields together uniquely identify a specific job posting.

2
Normalize it

Lowercase everything, trim whitespace from edges, strip special characters. This ensures "Software Engineer, NYC" and "Software Engineer, NYC" produce the same fingerprint.

3
Run SHA-256 hash

A mathematical function that turns the normalized text into a unique 64-character fingerprint. It's one-way — you can't reverse it — and deterministic — same input, always same output.

4
Check the database

Does a job with this exact hash already exist? The database has an index on the hash column so this lookup is nearly instant, even with millions of jobs stored.

5
If yes → skip silently. If no → save it.

Deduplication is silent — no errors, no logs, just a quiet skip. The second copy is discarded without ceremony.

A hash is like a fingerprint for data. Run the same text through SHA-256 twice, you get the exact same output. Change even one character, and the hash is completely different. This makes deduplication both fast and reliable.

How a PDF Becomes Data

A PDF is just pixels to a computer — it has no idea what a "skill" or "job title" is. Resume parsing uses an LLM to read the text and extract structured fields the scoring algorithm can use.

1
User uploads PDF

Browser sends it as a file to POST /api/resume — a dedicated API route that handles the upload.

2
pdf-parse extracts raw text

The pdf-parse library strips the PDF formatting and pulls out plain text from the buffer. Think of it as photocopying without the layout.

3
LLM reads and extracts fields

LLM reads the raw text and identifies: name, contact info, skills, work history, education, frameworks, and languages. It understands context, not just keywords.

4
Structured JSON saved to database

The extracted fields are formatted as JSON and saved to the resumes table in the database — one record per user.

5
All future scoring uses this data

Every job match score, every cover letter, every tailored resume — all powered by this structured data. The PDF is never re-read. Parse once, use everywhere.

This is called "structured extraction" — turning messy human text into machine-readable fields. It is one of the most valuable things you can do with an LLM, and it powers every feature that follows.

Why the Cover Letter Types Itself

Cover letters don't wait for the full AI response — they stream word by word using Server-Sent Events (SSE). The server keeps a connection open and sends text chunks the moment the AI generates them.

CODE 
function createSSEStream(req: Request) {
  const encoder = new TextEncoder();

  const stream = new ReadableStream({
    async start(controller) {
      const sendEvent =
          (event: string, data: any) => {
        const message =
          `event: ${event}\n` +
          `data: ${JSON.stringify(data)}\n\n`;
        controller.enqueue(
          encoder.encode(message));
      };

      const { userId } = await auth();
      if (!userId) {
        sendEvent("error",
          { message: "Unauthorized" });
        controller.close();
        return;
      }

      sendEvent("stage", {
        stageId: "stage1_load-job",
        name: "Loading job details...",
      });
PLAIN ENGLISH

createSSEStream(req) → Set up a live data channel — like opening a radio station that broadcasts as content is produced

new TextEncoder() → Converts JavaScript strings to bytes that the network can transmit

new ReadableStream({ start(controller) {...} }) → Create an open pipe — data will be pushed through it as it becomes available, not all at once

sendEvent(event, data) → Format and send one message in the SSE format: event type + JSON data + blank line separator

controller.enqueue(...) → Push one chunk of data through the pipe RIGHT NOW

await auth() → Verify the user is logged in before doing any AI work — check ID before letting anyone in

sendEvent("error", ...) → If not logged in, send an error event and close the connection

sendEvent("stage", {...}) → Tell the browser "stage 1 is starting" — this updates the progress indicator the user sees

Server-Sent Events (SSE) is a browser technology that keeps a connection open between server and browser. The server can push data at any time. This is how the cover letter appears to type itself — each chunk of words arrives as a separate event the moment the AI produces it.

Not Find-and-Replace — Actually Tailored

Tailoring your resume isn't just swapping keywords. Aladdin runs a two-pass pipeline that rewrites each bullet point individually, then polishes the whole thing for consistency.

Pass 1 Per-Bullet Rewrites
1
Parse resume PDF into structured data

Sections, roles, and individual bullet points are identified and stored as separate objects.

2
Embed the job description into vector chunks

The job description is split and converted to embeddings so we can find the most relevant parts for each bullet.

3
For each bullet: retrieve the most relevant job description chunks

Semantic search finds which parts of the job posting are most relevant to each specific bullet point.

4
Call LLM: "Rewrite this bullet to highlight the skills this job needs"

Each bullet is rewritten in context — it understands what this specific role is looking for.

Pass 2 Role Assembly
5
Combine all rewritten bullets for each work role

All the individually-rewritten bullets for each job are assembled back together as a role section.

6
Call LLM again: "Polish this role section — fix grammar, ensure consistent tone"

The second LLM call acts as an editor pass — it makes all bullets feel like they came from the same voice.

7
Run validators

Three safety checks: no deleted bullets — every original bullet must appear. No fabricated experience — no invented companies or roles. No invented skills — only skills from your original resume.

CODE 
export async function generateTailoredResume(
  params: GenerateTailoredResumeParams
): Promise<TailoredResumeOutput> {
  const { resumePdf, linkedinPdf,
    linkedinData, jobDescription } = params;
  const model =
    process.env.LLM_MODEL
    || "openai/gpt-4o-mini";

  const resumeBuffer =
    Buffer.isBuffer(resumePdf)
      ? resumePdf
      : Buffer.from(
          await (resumePdf as File)
            .arrayBuffer());

  const resumeParseResult =
    await parsePdfToDynamicResume(
      resumeBuffer);

  if (params.onProgress) {
    params.onProgress("complete",
      { stageId: "stage2_resume-parse" });
  }
PLAIN ENGLISH

GenerateTailoredResumeParams → Everything the pipeline needs: your resume PDF, optional LinkedIn PDF, and the target job description

const model = process.env.LLM_MODEL || ... → Which AI model to use — read from config so it can be swapped without code changes

Buffer.isBuffer(resumePdf) ? resumePdf : Buffer.from(...) → Handle two cases: PDF already in memory, or PDF coming as a File object that needs to be read

parsePdfToDynamicResume(resumeBuffer) → Extract text from the PDF bytes and structure it into JSON (roles, bullets, skills)

params.onProgress("complete", {...}) → Send a progress update to the streaming client — "Step 2 done!" updates the progress bar the user sees

The two-pass approach matters because a single-pass rewrite often produces inconsistent tone across bullets. Pass 2 is the "editor" pass — it makes everything coherent. Think of Pass 1 as a team of writers each drafting one sentence, and Pass 2 as a single editor reading the whole thing aloud.

How Aladdin Knows Which Jobs Are a Good Match

Before any AI is involved, a pure math algorithm scores each job 0–100 against your resume. No AI needed — just text matching and weighted arithmetic.

🎯
Role Match 30 pts

How similar is the job title to your past roles? Uses Jaccard similarity on shared words.

🛠️
Skill Match 50 pts

How many of your skills appear in the job description? More skills = more points, with diminishing returns past 15 matches.

📍
Location Match 10 pts

Remote job? Full 10 pts. Your city? 10 pts. Elsewhere? 5 pts. Location matters less than skills, so its weight is small.

📋
Base Score 10 pts

You uploaded a resume. That's worth something — every scored applicant starts with a floor of 10 points.

CODE 
// 3. ROLE MATCHING (30 Points)
const titleSimilarity =
  calculateTextSimilarity(
    jobTitle, targetRoles);
components.roleMatch =
  Math.min(30,
    Math.ceil(titleSimilarity * 100));

// 4. SKILL MATCHING (50 Points)
let foundSkills = 0;
allSkills.forEach(skill => {
  if (jobText.includes(skill)) {
    foundSkills++;
  }
});
components.skillMatch =
  Math.min(50,
    Math.ceil(foundSkills * 3.5));
PLAIN ENGLISH

calculateTextSimilarity(jobTitle, targetRoles) → Measure how similar two strings are: count the shared words, divide by total unique words (Jaccard similarity). Returns 0.0 to 1.0.

Math.min(30, Math.ceil(...)) → Cap at 30 points — role match can never exceed its category maximum

allSkills.forEach(skill => if(jobText.includes(skill))) → For each skill on your resume, check if that exact word appears in the job description

foundSkills++ → Count up every skill match

Math.ceil(foundSkills * 3.5) → 1 matching skill = 3.5 pts, 10 skills = 35 pts, 15+ skills → capped at 50 pts

What is a data access layer?

A data access layer is a centralized place for all database operations. The benefit: if you ever switch databases, you only change one file. The rest of the app is untouched.

Run Anywhere — PostgreSQL, Supabase, or SQLite

The same getJobs() function works whether you’re running on Neon Postgres in production, Supabase in staging, or SQLite on your laptop. The function detects which database is configured and routes to the right implementation.

CODE 

function getDbType():
    'postgres' | 'supabase' | 'sqlite' {
  if (process.env.DATABASE_URL
      ?.includes('neon.tech'))
    return 'postgres';
  if (process.env
      .NEXT_PUBLIC_SUPABASE_URL)
    return 'supabase';
  return 'sqlite';
}

export async function getAllPublicJobs(
  userId: string,
  options: GetJobsOptions
) {
  const dbType = getDbType();
  if (dbType === 'postgres')
    return getJobsFromPostgres(
      userId, options);
  if (dbType === 'supabase')
    return getJobsFromSupabase(
      userId, options);
  return getJobsFromSQLite(
    userId, options);
}
PLAIN ENGLISH

getDbType() → Look at environment variables to figure out which database is connected — like checking which power outlet you are plugging into.

process.env.DATABASE_URL?.includes(‘neon.tech’) → Is our database URL pointing at Neon? The ?. means “if this exists, then check” — safe even if the variable is missing.

process.env.NEXT_PUBLIC_SUPABASE_URL → Is the Supabase URL configured? If yes, we are in Supabase mode.

return ‘sqlite’ → If neither Postgres nor Supabase is configured, fall back to local SQLite — works offline with zero setup.

getAllPublicJobs(userId, options) → The public-facing function — callers never know which database runs underneath.

The if/else chain → Runtime routing: each call goes to the right backend transparently, like a switchboard operator connecting you to the right office.

🔀
Environment-based configuration

This pattern lets the same codebase run in development (SQLite), staging (Supabase), and production (Postgres) without a single code change — just different environment variables.

How Aladdin Learns What You Want

During onboarding, you answer 5 questions about the kind of jobs you want. Those answers become a scoring system that ranks every job in your feed.

work_areas (30 pts) → Does the job title match your preferred role family (Frontend, Backend, Full Stack)?
regions (25 pts) → Does the job location match your preferred regions?
role_types (20 pts) → Does the employment type match (full-time, internship, contract)?
work_style (15 pts) → Does the job match your preferred work style (remote, onsite, hybrid)?
career_levels (10 pts) → Does the seniority level match your career stage?
CODE 

export function computePreferenceScore(
  job: Job,
  answersByKey: Record<string,
    OnboardingAnswerRecord>
): number {
  let score = 0;

  const workAreasAnswer =
    answersByKey['work_areas'];
  if (workAreasAnswer) {
    const selected =
      toStringArray(workAreasAnswer.value);
    const titleLower =
      (job.title ?? '').toLowerCase();
    const matched = selected.some(
      (value) => {
        const keyword = value
          .replace(/_/g, ' ')
          .replace(/\s+engineer$/, '')
          .trim();
        return keyword.length > 0
          && titleLower.includes(keyword);
      });
    if (matched) score += 30;
  }
PLAIN ENGLISH

computePreferenceScore(job, answersByKey) → Given a job and your saved preferences, calculate how well the job matches what you told us you wanted.

let score = 0 → Start at zero — each matching preference adds points toward the total.

answersByKey[‘work_areas’] → Look up the work areas preference you chose (Frontend, Backend, etc.) by its key name.

toStringArray(...) → Convert the stored preference value into a plain list of strings we can loop over.

selected.some((value) => ...) → Does ANY of your preferred work areas match this job title? We only need one match.

value.replace(/_/g, ‘ ’) → Convert stored format (full_stack) to readable format (full stack) for title matching.

.replace(/\s+engineer$/, ‘’) → Remove “engineer” from the end so “frontend engineer” matches a “Frontend Developer” title too.

if (matched) score += 30 → Work areas match! Add 30 points — the highest-weight preference in the whole scoring system.

A Job Queue Without Redis

Most apps use Redis as a message queue for background jobs. Aladdin uses the database itself — each task is just a row in a table. The trick: a special SQL clause atomically claims tasks so no two workers grab the same one.

CODE 

async enqueue(
    input: EnqueueInput): Promise<void> {
  await this.withRetry(() =>
    this.prisma.jobQueue.create({
      data: {
        type: input.type,
        source: input.source ?? null,
        payload: input.payload
          as Prisma.InputJsonValue,
        status: 'pending',
        priority: input.priority ?? 2,
        runAt: input.runAt ?? new Date(),
        maxAttempts:
          input.maxAttempts
          ?? DEFAULT_MAX_ATTEMPTS,
        attempts: 0,
      },
    })
  )
}
PLAIN ENGLISH

enqueue(input) → Add a new task to the queue — like dropping a ticket into a dispenser.

this.withRetry(...) → If the database connection drops, retry once before giving up.

this.prisma.jobQueue.create({...}) → Insert a new row into the job_queue table — this IS the task. Prisma translates this to SQL for you.

status: ‘pending’ → New tasks start as “waiting to be picked up.”

priority: input.priority ?? 2 → Default priority is 2. Higher numbers run first.

runAt: input.runAt ?? new Date() → When to run this task. Default: immediately.

maxAttempts: ... ?? DEFAULT_MAX_ATTEMPTS → How many times to retry if it fails before marking as permanently dead.

attempts: 0 → Fresh task — has not been tried yet.

Task Lifecycle

1
pending

Waiting in the queue

2
processing

A worker has claimed and is running it

3
completed

Done successfully

4
failed

Error occurred — will retry up to maxAttempts

5
dead

Exceeded max retries — needs manual intervention

🔒
The secret sauce: FOR UPDATE SKIP LOCKED

FOR UPDATE SKIP LOCKED is a SQL clause that atomically claims a row for one worker while other workers skip it. This is how two workers can run at the same time without picking up the same task.

Five Patterns Every Production App Uses

The engineering patterns in Aladdin aren’t academic — they’re the same ones used at every major tech company.

🔀
Database Abstraction
One interface, multiple backends. Run on any database without changing business logic.
🔌
Adapter Pattern
One interface, multiple implementations. Add a new job source by writing one class — the pipeline handles the rest.
📋
Queue-Based Processing
Background tasks run in a queue, not on the web server. Heavy work doesn’t block user requests.
📡
Streaming Responses
Send data as it’s generated, not all at once. Users see progress instead of a loading spinner.
🔑
Content Deduplication
Hash-based fingerprinting ensures the same job from two sources is stored only once.
