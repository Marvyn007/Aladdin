What is a data access layer?

A data access layer is a centralized place for all database operations. The benefit: if you ever switch databases, you only change one file. The rest of the app is untouched.

Run Anywhere — PostgreSQL, Supabase, or SQLite

The same getJobs() function works whether you’re running on Neon Postgres in production, Supabase in staging, or SQLite on your laptop. The function detects which database is configured and routes to the right implementation.

CODE 

function getDbType():
    'postgres' | 'supabase' | 'sqlite' {
  if (process.env.DATABASE_URL
      ?.includes('neon.tech'))
    return 'postgres';
  if (process.env
      .NEXT_PUBLIC_SUPABASE_URL)
    return 'supabase';
  return 'sqlite';
}

export async function getAllPublicJobs(
  userId: string,
  options: GetJobsOptions
) {
  const dbType = getDbType();
  if (dbType === 'postgres')
    return getJobsFromPostgres(
      userId, options);
  if (dbType === 'supabase')
    return getJobsFromSupabase(
      userId, options);
  return getJobsFromSQLite(
    userId, options);
}
PLAIN ENGLISH

getDbType() → Look at environment variables to figure out which database is connected — like checking which power outlet you are plugging into.

process.env.DATABASE_URL?.includes(‘neon.tech’) → Is our database URL pointing at Neon? The ?. means “if this exists, then check” — safe even if the variable is missing.

process.env.NEXT_PUBLIC_SUPABASE_URL → Is the Supabase URL configured? If yes, we are in Supabase mode.

return ‘sqlite’ → If neither Postgres nor Supabase is configured, fall back to local SQLite — works offline with zero setup.

getAllPublicJobs(userId, options) → The public-facing function — callers never know which database runs underneath.

The if/else chain → Runtime routing: each call goes to the right backend transparently, like a switchboard operator connecting you to the right office.

🔀
Environment-based configuration

This pattern lets the same codebase run in development (SQLite), staging (Supabase), and production (Postgres) without a single code change — just different environment variables.

How Aladdin Learns What You Want

During onboarding, you answer 5 questions about the kind of jobs you want. Those answers become a scoring system that ranks every job in your feed.

work_areas (30 pts) → Does the job title match your preferred role family (Frontend, Backend, Full Stack)?
regions (25 pts) → Does the job location match your preferred regions?
role_types (20 pts) → Does the employment type match (full-time, internship, contract)?
work_style (15 pts) → Does the job match your preferred work style (remote, onsite, hybrid)?
career_levels (10 pts) → Does the seniority level match your career stage?
CODE 

export function computePreferenceScore(
  job: Job,
  answersByKey: Record<string,
    OnboardingAnswerRecord>
): number {
  let score = 0;

  const workAreasAnswer =
    answersByKey['work_areas'];
  if (workAreasAnswer) {
    const selected =
      toStringArray(workAreasAnswer.value);
    const titleLower =
      (job.title ?? '').toLowerCase();
    const matched = selected.some(
      (value) => {
        const keyword = value
          .replace(/_/g, ' ')
          .replace(/\s+engineer$/, '')
          .trim();
        return keyword.length > 0
          && titleLower.includes(keyword);
      });
    if (matched) score += 30;
  }
PLAIN ENGLISH

computePreferenceScore(job, answersByKey) → Given a job and your saved preferences, calculate how well the job matches what you told us you wanted.

let score = 0 → Start at zero — each matching preference adds points toward the total.

answersByKey[‘work_areas’] → Look up the work areas preference you chose (Frontend, Backend, etc.) by its key name.

toStringArray(...) → Convert the stored preference value into a plain list of strings we can loop over.

selected.some((value) => ...) → Does ANY of your preferred work areas match this job title? We only need one match.

value.replace(/_/g, ‘ ’) → Convert stored format (full_stack) to readable format (full stack) for title matching.

.replace(/\s+engineer$/, ‘’) → Remove “engineer” from the end so “frontend engineer” matches a “Frontend Developer” title too.

if (matched) score += 30 → Work areas match! Add 30 points — the highest-weight preference in the whole scoring system.

A Job Queue Without Redis

Most apps use Redis as a message queue for background jobs. Aladdin uses the database itself — each task is just a row in a table. The trick: a special SQL clause atomically claims tasks so no two workers grab the same one.

CODE 

async enqueue(
    input: EnqueueInput): Promise<void> {
  await this.withRetry(() =>
    this.prisma.jobQueue.create({
      data: {
        type: input.type,
        source: input.source ?? null,
        payload: input.payload
          as Prisma.InputJsonValue,
        status: 'pending',
        priority: input.priority ?? 2,
        runAt: input.runAt ?? new Date(),
        maxAttempts:
          input.maxAttempts
          ?? DEFAULT_MAX_ATTEMPTS,
        attempts: 0,
      },
    })
  )
}
PLAIN ENGLISH

enqueue(input) → Add a new task to the queue — like dropping a ticket into a dispenser.

this.withRetry(...) → If the database connection drops, retry once before giving up.

this.prisma.jobQueue.create({...}) → Insert a new row into the job_queue table — this IS the task. Prisma translates this to SQL for you.

status: ‘pending’ → New tasks start as “waiting to be picked up.”

priority: input.priority ?? 2 → Default priority is 2. Higher numbers run first.

runAt: input.runAt ?? new Date() → When to run this task. Default: immediately.

maxAttempts: ... ?? DEFAULT_MAX_ATTEMPTS → How many times to retry if it fails before marking as permanently dead.

attempts: 0 → Fresh task — has not been tried yet.

Task Lifecycle

1
pending

Waiting in the queue

2
processing

A worker has claimed and is running it

3
completed

Done successfully

4
failed

Error occurred — will retry up to maxAttempts

5
dead

Exceeded max retries — needs manual intervention

🔒
The secret sauce: FOR UPDATE SKIP LOCKED

FOR UPDATE SKIP LOCKED is a SQL clause that atomically claims a row for one worker while other workers skip it. This is how two workers can run at the same time without picking up the same task.

Why Every API Route Starts With auth()

Authentication is handled by Clerk — a third-party service that manages user accounts and session tokens. The app calls auth() at the start of every API route to verify who’s asking.

Five Patterns Every Production App Uses

The engineering patterns in Aladdin aren’t academic — they’re the same ones used at every major tech company.

🔀
Database Abstraction
One interface, multiple backends. Run on any database without changing business logic.
🔌
Adapter Pattern
One interface, multiple implementations. Add a new job source by writing one class — the pipeline handles the rest.
📋
Queue-Based Processing
Background tasks run in a queue, not on the web server. Heavy work doesn’t block user requests.
📡
Streaming Responses
Send data as it’s generated, not all at once. Users see progress instead of a loading spinner.
🔑
Content Deduplication
Hash-based fingerprinting ensures the same job from two sources is stored only once.
